# 测试驱动开发

## 概述

TDD 是面向可执行行为的实现内循环：先写测试→看它失败→写最小代码通过→重构。

**核心原则：** 没亲眼看到测试失败，就不知道它是否测试了正确的东西。

TDD 不替代需求、概览设计和详细设计。只在任务有明确行为契约且验证对象适合自动化测试后才开始。

## 何时使用

**适用：** 可执行代码行为、可复现的 bug 修复、CLI 行为、解析器/校验器/状态机等确定性逻辑、需保持稳定契约的重构

**不适用：** 需求/设计工作、文档语义、协作协议、需通过代理行为而非代码输出判断的技能规则

## Red-Green-Refactor

### RED —— 写一个失败的测试

写一个最小的测试，展示代码应该做什么：
- 一个行为、清晰的名称、用真实代码（非 mock）

看它**正确失败**——因为功能缺失而失败，不是因为拼写错误。测试直接通过了？说明在测已有行为，修正测试。

### GREEN —— 最小代码

写最简单的代码让测试通过。不加功能、不重构其他代码、不超过测试范围"改进"。

### REFACTOR —— 清理

全绿之后：消除重复、改善命名、提取辅助函数。保持全绿，不添加行为。

## 为什么顺序重要

- **实现后写测试**：测试立即通过证明不了任何事——可能测错了东西、可能测的是实现而非行为、可能遗漏了你忘记的边界情况
- **手动测试**：临时性的，没有记录、代码变更时无法重跑
- **"删除 X 小时的工作太浪费"**：沉没成本谬误。已经花掉的时间回不来了。保留你无法信任的代码才是真正的浪费

## 警示信号

出现以下任一情况，删除代码重新用 TDD：
- 测试之前就有可执行生产代码
- 测试立即通过
- 无法解释为什么测试失败
- 各种"仅此一次"的合理化借口

## 要点

- Bug 修复也必须用失败测试复现
- 测试难写 = 设计难用，倾听测试的反馈
- 不要用 mock 替代真实代码，除非不可避免
