# 详细设计

> 章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。
>
> **使用前先确认你能回答这些问题**：
> - 哪些文件会新增或修改，为什么是这些地方？
> - 涉及哪些接口、契约和稳定边界？精度需要细到什么程度？
> - 模块内部职责如何拆分？谁负责状态变化、校验、编排和副作用？
> - 关键数据结构、字段语义或状态转换约束是什么？
> - 准备怎么验证这轮工作真的成立？如果主验证路径走不通，降级路径是什么？
> - testing-first / verification-first 的实施顺序是什么？
> - observability 要求是什么？要靠什么看见失败或退化？
> - 失败路径、误用风险和静默出错风险是什么？
> - 迁移顺序和回滚注意事项是什么？
> - 还有哪些挑战被接受、拒绝或延期？
> - 哪些交互关系最适合用 PlantUML 表达？
>
> **写法建议**：先把实现设计写到足以判断验证对象，再写验证路径（否则容易让测试或命令替代真实设计）。Files Added Or Changed 不只是改动清单，更是"为什么这些地方承载本轮实现"的解释。模块内部职责、数据语义和异常边界要写到 agent 能直接据此落实现。如果你写完后还不能直接开始实施，说明 detailed 还不够具体。

## 可观察性与验证准备
- **验证路径**：用中文列出将执行的验证路径，命令本身保持英文原样；先写主验证路径，再写 fallback。
- **回退路径**：用中文说明如果主验证路径被阻塞时如何处理，以及何时不能宣称完成。
- **预期证据**：用中文写明预计要产出的证据、产物或观察结果，并说明后续 `verification-design.md` 需要收什么。

**完成标准**：至少写主验证路径、阻塞时的 fallback 和预期证据。这里必须体现 testing-first / verification-first：先准备适合对象的测试或验证，再落实现；它不等于默认先写 pytest。

只有当详细设计已经具体到可以执行时，才进入 `implementing`。
如果设计已经完成但实现尚未开始，应保持在 `detailed_designed`。

## 新增或修改文件
用中文列出将新增或修改的文件，并说明它们为什么在这轮需要变化。

**完成标准**：至少说明每类改动文件的作用。不接受只有文件清单、没有承载理由的写法。

## 接口
用中文写清楚这轮改动暴露或依赖的接口、契约和稳定边界。

**完成标准**：至少定义稳定边界、接口精度（参数语义、输入输出约束、边界条件、错误传播或兼容性要求）和暴露契约。交代关键 observability 入口（日志、状态、测试观察点、验证产物），能说清怎么观察失败或退化。

## 模块内部设计
用中文说明关键模块的内部职责分解：编排、校验、状态更新、副作用、适配层分别落在哪里。

**完成标准**：至少说明一个关键模块的内部职责分解。这里是把 overview 的结构边界下沉到足够支撑编码的层次，但仍不记录执行结果。

## 数据语义
用中文说明关键数据结构、字段语义、状态转换或一致性约束。如果关系复杂，说明是否需要用 PlantUML 状态图、类图或关系图辅助表达。

**完成标准**：至少说明一个关键数据结构、字段语义或状态转换约束。

## 阶段门禁
用中文写清楚 detailed 要进入实施前必须确定的硬条件。

**完成标准**：至少覆盖实现落点、模块内部职责、接口精度、数据语义、迁移顺序、测试或验证策略、observability 要求和预期证据类型。

## 决策闭合
用中文记录关键挑战如何被处理。只允许写：接受（含理由）、拒绝（含理由、替代方案）、延期（含触发条件）。

**完成标准**：至少记录一个被接受、拒绝或延期的关键挑战，并带各自理由。

## 错误处理
用中文说明失败路径、误用风险、校验边界和如何避免静默出错。

**完成标准**：至少写出一个静默出错风险，并交代异常如何传播或回退。如果异常处理跨模块传播，应写清传播链。

## 迁移说明
用中文描述迁移顺序、兼容策略、落地阶段和回滚注意事项，说明切换点与回滚触发点。

**完成标准**：至少写出实施顺序、切换点和回滚触发点。没有迁移笔记 = 默认"改完就生效"，生产环境从没有这种事。

## 推荐图示
如果关键交互、状态变化或数据关系仅靠文字容易歧义，用中文说明推荐补哪些 PlantUML 图（时序图、状态图、数据关系图等）。

**完成标准**：如果图示能显著减少歧义，应给出推荐图类型或图示位置。图不能替代文字里的接口、数据语义和异常说明。

## 详细设计反思
用中文记录对测试策略、接口边界、迁移假设和验证路径的反思。

**完成标准**：至少再次挑战测试策略、接口、迁移和预期证据假设。
