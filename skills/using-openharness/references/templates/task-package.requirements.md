# 需求

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。

## 背景

当前上下文：项目现状、相关模块、已有基础设施。不需要长篇大论，但要让零上下文读者能定位"这是在哪个项目里、动的是哪一块"。如果涉及已有任务包或历史决策，在此引用。

## 问题陈述

当前痛点、缺口或风险是什么？为什么现在做而不是以后？

写清楚：谁在用、在什么场景下、遇到了什么问题。读者不需要额外解释就能理解"现在的状况为什么不可接受"。

## 目标

做完以后什么事实会成立？

必须具体可验证——不能只写"提升""优化""增强"。写完应能直接回答"怎么判断做完还是没做完"。

## 交付物

本轮必须产出的东西，按可验证的粒度写清验收标准。每一项交付物后续都应该能在验证设计中找到对应的验证方法。

## 非目标

本轮明确不做什么。至少写一个反例——看起来相关但不属于本轮的情况。这是防止范围膨胀的围栏。

## 约束

当前不能突破的协议或兼容性边界、依赖条件、预算限制。如果某个限制被突破后会变成另一个任务包，也在这里注明。

## 自检

提交前确认：

- [ ] 不了解本轮对话的人，读完「背景」和「问题陈述」，能否知道当前矛盾是什么、为什么现在做？
- [ ] 「目标」和「交付物」是否足够具体，不需要口头补充就能判断做完还是没做完？
- [ ] 「非目标」是否写了具体的反例？
- [ ] 「约束」是否写清了不可突破的边界？
