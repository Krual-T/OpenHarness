# 需求

> 章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。
>
> **使用前先确认你能回答这些问题**：
> - 为什么现在要做这件事，而不是以后再做？
> - 当前痛点、缺口、冲突或风险具体是什么？
> - 本轮必须交付哪些结果？这些结果的验收标准是什么？
> - 本轮明确不做什么？哪个 counterexample 看起来相似，但仍然不属于这个任务包？
> - 目标用户是谁？核心场景是什么？单一成功指标是什么？
> - 本轮允许付出的 cost cap 是什么？
> - 有哪些不能违反的约束？
>
> **写法建议**：先写问题陈述（当前到底哪里痛），再写必须交付的结果（准备交付什么），不要倒过来。模板里的每个标题都是必答题。如果你写完后仍然无法解释"为什么不是另一个问题包"，说明需求还没收敛。

## 目标
用中文写清楚这项工作的目标，说明希望达到的结果，并写明单一成功指标。

**完成标准**：至少写清希望达成的真实结果，不能只包含"提升""优化""增强"这类抽象词。应该能回答"做完以后什么事实会成立"。

## 问题陈述
用中文说明当前痛点、缺口、冲突或风险，解释为什么现在要做这件事。

**完成标准**：至少写清当前矛盾、目标用户、核心场景和为什么现在要做。至少要写出一个已经存在的矛盾，而不是只写未来愿景。

## 必须交付的结果
1. 用中文写出必须交付的结果，按可验证的粒度列清楚，并为核心结果写验收标准。

**完成标准**：至少按可检查粒度列出必须交付物。这里的每一项，后续都应该能在 `verification-design.md` 里找到对应验证。

## 非目标
- 用中文写明本轮明确不做什么，避免范围漂移。

**完成标准**：至少写一个 `counterexample`，说明"看起来相关但不属于本轮"的情况。

## 约束
- 用中文写明协议限制、兼容性约束、依赖条件、`cost cap` 和不可变边界。

**完成标准**：至少写清当前不能突破的协议或兼容性边界，以及本轮 cost cap。如果某个限制被突破就会变成另一个 task package，也写在这里。
