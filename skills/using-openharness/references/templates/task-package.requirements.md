# 需求

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。
>
> **写前确认**：
> 1. 当前痛点、缺口或风险是什么？为什么现在做而不是以后？
> 2. 本轮必须交付哪些结果？各自的验收标准是什么？
> 3. 本轮明确不做什么？至少想出一个反例——看起来相关但不属于本轮。
> 4. 目标用户是谁？核心场景是什么？
> 5. 成本上限和不可违反的约束是什么？
>
> **写法要点**：先写问题陈述，再写交付结果。如果你写完后说不清"为什么这不是另一个任务"，说明需求还没收敛。

## 目标
用中文写清这项工作的目标和单一成功指标。

**完成标准**：目标必须具体可验证，不能只写"提升""优化""增强"这类抽象词。写完应能回答"做完以后什么事实会成立"。

## 问题陈述
用中文说明当前痛点、缺口、冲突或风险，解释为什么现在要做。

**完成标准**：至少写出一个已经存在的矛盾，并说明目标用户和核心场景。

## 必须交付的结果
1. 用中文列出必须交付的结果，按可验证的粒度写清验收标准。

**完成标准**：每项结果都应能在后续 `verification-design.md` 中找到对应的验证方法。

## 非目标
- 用中文写明本轮明确不做什么。

**完成标准**：至少写出一个反例——看起来相关但不属于本轮的情况。

## 约束
- 用中文写明协议限制、兼容性要求、依赖条件、成本上限和不可变边界。

**完成标准**：写清当前不能突破的协议或兼容性边界，以及本轮成本上限。如果某个限制被突破后会变成另一个任务包，也应注明。
