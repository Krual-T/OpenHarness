# 计划设计

## 目标

`plan.md` 是实现计划：把已经确认的需求和已有设计结论转成可审阅、可执行、可验证的工作清单。它不是任务类型判断阶段，也不是新的总体设计或详细设计。

{% if task_type == "standard" %}
当前任务是 `standard`：本阶段从 `requirements.md` 直接推出实现计划。由于本工作流没有单独的总体设计和详细设计，可以在「文件修改计划」里写必要的实现落点、职责边界和执行顺序，但不要展开成架构设计。
{% elif task_type == "structural" %}
当前任务是 `structural`：本阶段消费 `requirements.md`、`overview-design.md` 和 `detailed-design.md`。不要重新讨论模块边界、接口语义、数据语义或方案取舍；如果发现设计结论无法支持执行，回退到对应设计阶段修正。
{% else %}
当前任务类型未渲染为 `standard` 或 `structural`。本阶段只应由需要计划的工作流进入；如果上下文缺失，先检查 `task-info.yaml.collaboration.task_type` 和当前 workflow。
{% endif %}

## 输入文档

{% if task_type == "standard" %}
读取并只消费：

- `requirements.md`：交付物、非目标、验收标准、约束。
{% elif task_type == "structural" %}
读取并只消费：

- `requirements.md`：交付物、非目标、验收标准、约束。
- `overview-design.md`：系统边界、推荐结构、关键流程、架构约束。
- `detailed-design.md`：实现落点、接口精度、模块内部职责、数据语义、迁移说明。
{% else %}
读取 `requirements.md`；如任务实际上依赖设计文档，先确认 workflow 和 `task_type` 是否正确。
{% endif %}

## 步骤

1. **提取执行输入**：列出本轮必须交付的结果、明确不做的范围、已经确定的设计结论和验证约束。
2. **写目标与上下文**：用几句话说明本计划要完成什么、当前相关代码或文档状态是什么、实现者需要知道哪些文件或术语。
3. **制定实施步骤**：把工作拆成可勾选子任务。每个子任务都写清修改对象、完成条件和验证方式；步骤要按可执行顺序排列。
4. **制定文件修改计划**：列出预计修改或新增的文件，并说明每个文件承载什么职责。
{% if task_type == "standard" %}
   - 可以在这里写必要的实现落点、局部职责边界和执行顺序。
   - 不要把局部落点扩写成总体设计；如果已经需要系统拆分、跨模块接口或状态模型设计，应回退需求阶段改为 `structural`。
{% elif task_type == "structural" %}
   - 只引用 overview/detailed 已确认的落点和边界。
   - 不要在这里新增模块边界、接口语义或数据语义；发现缺口时回退设计阶段。
{% endif %}
5. **制定验证设计**：按 `task-info.yaml.verification.method` 写验证命令或审核矩阵，并写清预期结果、边界或错误场景。
{% if verification_method == "unit_test" %}
   - `unit_test`：列出测试文件、测试命令、预期失败/通过信号。
{% elif verification_method == "qualitative" %}
   - `qualitative`：明确审核对象、审核标准、判定准则和审核矩阵；审核需由子 Agent 和人类审阅者双轨执行，两方结论均需记录。
{% else %}
   - 当前未设置 verification.method，请先确认验证方式后再继续。
{% endif %}
{% if rwp_enabled == "true" %}
   - `rwp.enabled: true`：在主要验证方法之外，选择或编写运行时工作流脚本。
{% endif %}
6. **记录进度、决策与发现**：如果计划执行可能跨多轮或多人协作，预留进度记录、执行中发现和决策记录，让后来者只看 `plan.md` 也能恢复上下文。
7. **写完成判定和风险接受**：说明何时可以进入实现、何时可以进入验证、哪些风险本轮接受。

## `plan.md` 推荐结构

使用一套模板，不按任务类型拆成两份：

- `## 目标与上下文`
- `## 输入文档`
- `## 实施步骤`
- `## 文件修改计划`
- `## 验证设计`
- `## 进度记录`
- `## 决策与发现`
- `## 风险接受`
- `## 完成判定`

短任务可以把「进度记录」和「决策与发现」写得很短，但不要删除实施步骤、文件修改计划、验证设计和完成判定。

## 计划确认停点

写完 `plan.md` 后，必须向用户展示：

- 实施步骤清单。
- 文件修改计划。
- 验证命令或审核矩阵。
- 每项交付物对应的验证方式。
- 本轮不覆盖的风险和接受理由。

获得用户确认后才可 transition。用户否定 → 修正计划。

[可选] 在计划阶段就跑一次验证命令确认能正确失败，提前暴露验证设计自身的问题。

## 阶段结束检查

1. 每项交付物是否都有对应实施步骤？
2. 每个实施步骤是否都有修改对象、完成条件和验证方式？
3. 文件修改计划是否说明了每个文件的职责？
4. 验证命令是否具体到可以直接复制粘贴执行，或审核矩阵是否能逐项判定？
5. 是否有至少一个边界或错误场景的验证？
6. 是否明确了本轮不覆盖的风险和接受理由？
{% if task_type == "standard" %}
7. `plan.md` 是否只写必要的轻量实现设计，没有展开成架构设计？
{% elif task_type == "structural" %}
7. `plan.md` 是否只消费 overview/detailed 的设计结论，没有重新做总体设计或详细设计？
{% else %}
7. `plan.md` 是否只安排执行和验证，没有重新做任务类型判断？
{% endif %}

全部能回答 → `openharness task-package transition <task-name>|<task-id> planned`

`planned` 是 gate 状态，CLI 会自动推进到 `implementing` 并输出实现阶段指令。

## verification.method 一致性校验

`verification.method` 和 `verification.rwp` 已在需求阶段确定。本阶段只校验当前值是否仍然匹配验证对象；如果冲突，**阻塞**——回到 `requirements.md` 和 `task-info.yaml` 重新确定验证配置。

{% if verification_method == "unit_test" %}
验证对象必须满足：输入输出可编程、无外部副作用、失败可自动判定。不能用 `unit_test` 验证代码可读性、设计意图或自然语言语义。
{% elif verification_method == "qualitative" %}
验证对象必须是设计文档、API 契约、命名规范、协议意图等语义产物；审核必须由子 Agent 和人类审阅者双轨执行。不能用 `qualitative` 验证可编程函数返回值。

## 文档与字符级断言边界

文档修改不得默认使用 `pytest`。只有当文本本身是稳定契约时，才设计字符级断言或最小化结构测试。

适合字符级断言的对象：

- 命令名、参数名、状态值、YAML 键名、文件名、路径。
- 固定章节标题、模板占位符、机器或 Agent 会依赖的协议锚点。
- 已确认废弃的入口、字段或旧写法，用于防止回归。
- 安装、运行或复制执行示例中的关键命令字符串。

不适合字符级断言的对象：

- 自然语言是否清楚、完整、符合设计意图。
- 需求、设计、证据正文的普通措辞、段落顺序或同义改写。
- 只用普通关键词证明主题已覆盖，例如 `assert "验证" in text`。
- 用完整自然语言句子断言语义正确，导致正常改写被误判为失败。

如果验证对象是自然语言语义、协议意图、设计正确性或命名规范，使用 `qualitative` 审核。若本阶段发现当前 `verification.method` 与对象性质冲突，回到 `requirements.md` 和 `task-info.yaml` 修正，不在本阶段临时切换。

## qualitative 审核矩阵

`plan.md` 必须写清审核矩阵，让子 Agent 和人类审阅者拿到同一份审核输入。

审核矩阵至少包含：

- **审核对象**：文件路径、章节范围和本轮实际改动。
- **任务背景**：为什么修改、要解决什么问题、本轮边界是什么。
- **审核目标**：本轮要判断的语义问题。
- **审核矩阵**：审核对象、审核维度、通过标准、证据要求。
- **非审核范围**：明确不评价什么，避免审核扩大到本轮外。
- **输出格式**：结论、逐项发现、证据缺口、风险接受。

审核矩阵的判定标准必须能让子 Agent 和人类审阅者逐项回答“通过 / 有条件通过 / 不通过”。不能只写“审查是否合理”“看起来是否清楚”。
{% endif %}

{% if rwp_enabled == "true" %}
### RWP 选择与设计约束

- **必须包含单元测试**：RWP 不是纯工作流——代码单元的正确性仍需要单元测试保障。`## 验证设计` 中必须列出单元测试命令，不可只写工作流命令。
- **优先复用**现有 RWP（`openharness rwp list` 查看）。不要为每一个任务写新工作流脚本。
- **必须声明**运行环境依赖（Python 版本、系统包、网络条件）和清理行为（工作流结束后是否需要手动回收资源）。
- **必须明确**退出码语义：0 通过 / 1 失败 / 其他 = 环境异常。
- 工作流脚本的 stdout 和 stderr 不可混用——stdout 放结构化产物，stderr 放人类可读日志。
- **预期结果必须可逐项比对**：verifying 阶段会由子 Agent 读取工作流输出，对照 `## 验证设计` 逐项比对。
{% endif %}

## 失败回退

计划阶段如果卡住，不要强行推进：

| 卡住原因 | 回退动作 |
|---------|---------|
| 某项交付物找不到对应实施步骤 | 回到 `requirements.md` 修正交付物边界 |
| 某项实施步骤找不到验证方式 | 拆细步骤，或回到 `requirements.md` 修正确认标准 |
| 文件修改计划无法说明职责 | 重新阅读输入文档；如果仍无法确定，回退需求或设计阶段 |
| 验证命令无法精确到复制粘贴执行 | 补充文件路径、参数、环境变量 |
| 验证配置与需求性质冲突 | 回退需求阶段，修正 `requirements.md` 和 `task-info.yaml` 后再重新进入计划 |
{% if task_type == "standard" %}
| 计划需要系统拆分、跨模块接口或状态模型设计 | 回退需求阶段，将任务改为 `structural` |
{% elif task_type == "structural" %}
| 计划阶段发现设计结论缺失或冲突 | 回退到 `overview-design.md` 或 `detailed-design.md` 修正设计 |
{% endif %}
{% if verification_method == "qualitative" %}
| 文档语义被写成 pytest 字符串断言 | 回到 `plan.md` 改为 `qualitative` 审核矩阵；只保留稳定文本契约断言 |
| 定性审核矩阵缺字段 | 补齐审核对象、背景、目标、矩阵、非审核范围和输出格式 |
{% endif %}
| 无法决定边界场景的验证粒度 | 优先覆盖安全/数据完整性边界；低风险边界可声明不覆盖 |

## 要点

- `plan.md` 是执行清单，不是缩写版总体设计或详细设计。
- 一套 `plan.md` 模板即可；`standard` 和 `structural` 的差异由本阶段指令按 `task_type` 渲染。
- `standard` 允许写必要的轻量实现设计；`structural` 只消费已有设计结论。
- 不要在计划阶段重新争论模块结构；如果发现结构设计不成立，回到对应设计阶段。
- `## 验证设计` 中每条命令的期望退出码必须写明。
- implementing 阶段按 `plan.md` 的实施步骤执行；verifying 阶段按 `plan.md` 的验证设计判定。
{% if verification_method == "qualitative" %}
- 对 `qualitative` 任务，审核矩阵就是主要验证计划；不要为了凑命令而编造 pytest。
{% endif %}

## 常见失败模式

- 把 `plan.md` 写成愿望列表，没有可勾选步骤。
- 每个步骤只有“修改代码”，没有完成条件和验证方式。
- 只写实施步骤，不写文件修改计划，导致实现者不知道每个文件承担什么职责。
- 把验证命令写成抽象描述（“运行测试”），而非可执行命令（`pytest tests/test_xxx.py -v`）。
- 在 `standard` 的 `plan.md` 里写成完整架构设计。
- 在 `structural` 的 `plan.md` 里重新设计 overview/detailed 已经确定的内容。
- 对所有能想到的验证都塞进去，导致 implementing 阶段验证负担过重。
{% if verification_method == "qualitative" %}
- 对自然语言文档默认设计 `pytest`，把“测试通过”误当成“文档语义正确”。
- 定性验证只写“请帮我看一下”，没有审核矩阵和非审核范围。
- 定性验证只安排了 AI 审核未安排人类审核。
{% endif %}
