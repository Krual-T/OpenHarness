# 系统化调试

## 概述

随机修复浪费时间并创造新 bug。先找到根因再动手。

## 四阶段流程

### 阶段 1：根因调查

**修复前必须完成：**

1. 仔细阅读错误信息：完整阅读堆栈跟踪，注意行号、文件路径、错误码
2. 稳定复现：能否可靠触发？确切的复现步骤是什么？
3. 检查最近变更：`git diff`、最近提交、新依赖、配置变更、环境差异
4. 多组件系统中收集证据：在每层组件边界记录输入/输出数据，确定故障发生在哪一层
5. 追踪数据流：坏数据从哪里来？谁传的？一直追踪到源头。在源头修复，不在症状处修复

### 阶段 2：模式分析

1. 在同一代码库中找到类似但正常工作的代码作为参照
2. 完整阅读参考实现，不要略读
3. 逐项列出正常和异常之间的差异
4. 理解依赖：还需要哪些其他组件、设置、环境？

### 阶段 3：假设与测试

1. 形成单一假设："我认为 X 是根因，因为 Y"
2. 做最小改动来测试假设，一次只改一个变量
3. 验证结果：有效→阶段 4；无效→形成新假设，不要叠加更多修复

### 阶段 4：实施修复

1. 先创建失败的测试用例来复现 bug
2. 实施单一修复，一次只改一处
3. 验证：测试通过了吗？其他测试没受影响吗？
4. 如果修复无效：已尝试几次？
   - < 3 次：带着新信息回到阶段 1
   - ≥ 3 次：停下来质疑架构——每次修复都在不同地方暴露新问题，说明可能是架构问题，与用户讨论后再继续

## 警示信号

发现自己有以下想法时，立即回到阶段 1：
- "先快速修一下，之后再调查"
- "试试改 X 看看效果"
- "可能是 X，我来修掉"
- "再试一次修复"（已经试了 2 次以上）
- 在追踪数据流之前就提出解决方案

## 常用借口对照

| 借口 | 事实 |
|------|------|
| "问题简单不需要流程" | 简单问题也有根因，流程对简单 bug 也很快 |
| "紧急没时间走流程" | 系统化调试比猜测试错更快 |
| "先试试这个再说" | 第一次修复就定调子，从一开始就做对 |
| "我看到问题了让我修" | 看到症状 ≠ 理解根因 |
