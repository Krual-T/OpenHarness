# 完成前验证

## 概述

没有验证就声称完成是不可靠的。**先有证据，再下结论。**

## 验证流程

在声称任何状态或表达满意之前：

1. **确认路径**：什么验证路径能证明这个结论？（命令验证 / 文档审核 / 手动运行时验证 / 验证不足）
2. **执行**：重新运行完整验证命令或手动验证步骤
3. **读取**：完整输出，检查退出码、失败、盲区
4. **文档语义审核**（当验证对象包含任务包文档时）：
   - 读取对应 guidance 文件作为审核标准
   - 调度文档审核子代理执行语义审查（参考 `reviewing-task-package` skill）
   - 审核不通过 → 修改文档后重新进入步骤 2
5. **确认**：证据是否支撑结论？
   - 否 → 陈述实际状态及证据
   - 验证不足 → 说明阻塞的完成状态和缺失的证据
   - 是 → 带证据陈述结论
6. **仅在此之后**做出声明

跳过任何一步 = 没有真正验证。

## 常见错误（反合理化）

这些声明在没有对应证据时不成立：

| 声称 | 需要 | 不够 |
|------|------|------|
| 测试通过 | 测试命令输出：0 失败 | 上一次运行、"应该能通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来正常 |
| Bug 修复 | 测试原始症状：通过 | 代码改了、假设修好了 |
| 子代理完成 | VCS diff 显示变更 | 子代理报告"成功" |
| 文档通过 | 语义审核通过 | 程序化验证通过、章节齐全 |

### 为什么这些借口不成立

| 借口 | 为什么不成立 |
|------|-------------|
| "测试上次跑过了" | 代码变了。上次的通过不能证明这次没问题。 |
| "应该没问题" | "应该"不是证据。验证需要实际运行结果。 |
| "看起来正常" | "看起来" = 没检查。没有可观测证据就没有完成。 |
| "子代理报告成功" | 子代理可能遗漏、误会指令或产生幻觉。必须对照 VCS diff 核实。 |
| "机械性验证过了" | 程序化验证只检查形式（章节存在），不检查语义（内容是否有信息量）。 |

## 警示信号

出现以下情况立即停止：
- 使用"应该"、"可能"、"似乎"
- 在验证前表达满意（"好了！"、"完成了！"）
- 信任子代理的成功报告
- 仅做部分验证就下结论
- 疲劳想收工——疲劳不等于验证

## 阶段写回

声称完成前写好验证阶段产物：
- `04-verification.md`：记录计划路径、执行路径、可追溯性、结果和已接受的残留风险
- `05-evidence.md`：记录变更文件、执行的命令、产物路径、手动步骤、残留风险、后续事项

两者读起来仍像占位符即表示阶段未实际关闭。

## 验证失败时

验证结果不支撑完成主张时：
1. 陈述实际状态及证据，不要推断"应该能通过"
2. 区分失败类型：代码行为失败 → 调用 `systematic-debugging`；文档质量不足 → 调用 `reviewing-task-package`
3. 修复后重新验证，不要跳过重验步骤直接推进状态
