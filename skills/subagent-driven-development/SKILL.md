# 子代理驱动开发

## 何时使用

同时满足以下条件：
- 任务包已准备好执行
- 工作可拆分为基本独立的子任务
- 用户明确要求子代理或并行工作
- 调度不会产生比本地执行更麻烦的共享写入冲突

不满足则不使用，在主会话中手动执行。

## 步骤

1. 读一遍任务包，提取可执行任务到本地清单
2. 为每个任务准备上下文：确切的任务文本、相关文件路径、约束和验收标准
3. **判断并发性**：
   - 多个子任务互不依赖、不编辑同一文件、不共享写入状态 → 可以并发调度
   - 否则每次调度一个子代理
4. 调度子代理完成边界清晰的任务
   - 串行时：每次一个，完成并审查后再下一个
   - 并发时：一次性调度所有独立任务，但每个任务仍要边界清晰
5. 子代理有疑问时先回答，不要让它在歧义中猜测
6. 对照任务包和验证路径审查结果
   - 并发返回后：先检查文件冲突，再逐一审查
7. 有缺口则给出具体修正意见后重新调度
8. 子代理结果验证通过后才标记本地清单中的任务完成
9. 全部完成后运行包级验证，更新 `04-verification.md`、`05-evidence.md` 和 `STATUS.yaml`

## 模型选择

- 机械性、范围紧的编辑：快速模型
- 多文件集成工作：标准模型
- 架构判断或审查密集型工作：最强可用模型

不要用更强的模型来弥补模糊的任务描述。

## 处理子代理状态

- **DONE**：对照任务包审查结果并运行验证
- **DONE_WITH_CONCERNS**：先阅读疑虑再继续，解决正确性或范围问题后再视为完成
- **NEEDS_CONTEXT**：补充缺失上下文后重新调度
- **BLOCKED**：改变上下文、任务大小或模型后再试，不要盲目重试相同的 prompt

## 并发调度规则

允许并发当且仅当同时满足：
- 每个子任务修改的文件集合互不重叠
- 子任务之间没有读取-执行-写入的依赖链
- 用户明确要求或任务包已明确标注可并发

**并发前检查清单**：
1. 列出每个子任务预计修改的文件
2. 检查是否有文件出现在多个子任务的列表中
3. 有重叠 → 串行；无重叠 → 可以并发

**并发后合并**：
1. 所有子代理返回后，检查是否有文件冲突
2. 运行完整验证（测试 + 文档审核）
3. 合并后的变更仍需一次性审查

## 要点

- 用户未要求调度时不要使用
- 让子代理自己去发现任务包不如直接把任务内容交给它
- 不要调度多个会编辑同一文件的子代理（并发前必须检查文件冲突）
- 子代理自报完成不等于已完成
- 并发子代理返回后要先做冲突检查再做结果审查
- 包验证和证据写回完成前不算结束
