# 需求

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。

## 背景

OpenHarness 通过任务包和阶段技能指导 AI 协作者完成代码、文档和协议改动。当前验证阶段已经支持 `unit_test`、`qualitative`、`rwp` 三类验证方式，但对文档修改的验证边界仍不够具体。

近期使用中暴露出一个反复问题：AI 容易在修改自然语言文档后默认运行 `pytest`，或者用字符包含断言来证明文档语义正确。这类做法会把“代码测试通过”误当成“文档内容正确”，也会让本应由子智能体和人工阅读判断的语义审核流于形式。

## 问题陈述

使用 OpenHarness 的 AI 协作者在处理文档、协议和技能说明时，需要知道哪些内容适合自动断言，哪些内容必须交给定性审核。目前协议只说明 `qualitative` 适合文档、契约、命名规范等语义产物，但没有进一步说明：

- 字符级断言在什么情况下是稳定契约，例如命令、状态值、YAML 键、文件名、路径、固定章节标题、废弃入口防回归。
- 字符级断言在什么情况下会变成脆弱测试，例如断言自然语言句子、普通关键词、段落措辞和任务包正文语义。
- 自然语言定性审核需要如何交接给子智能体和人工审阅者，才能得到可追溯的审核结论，而不是一句“看起来可以”。

如果不补上这套规则，后续文档类任务会继续混用 `pytest`、宽泛字符串断言和主观阅读结论，验证证据的可信度会下降。

## 目标

本轮完成后，OpenHarness 协议应明确以下事实：

- 文档修改不能默认使用 `pytest` 作为验证方式。
- 字符级断言只用于稳定文本契约、机器入口、可复制执行内容和已知回归哨点。
- 自然语言语义、清晰度、设计正确性和协议意图应通过 `qualitative` 审核验证。
- `qualitative` 审核应有明确交接包，包含审核对象、背景、目标、审核矩阵、非审核范围和输出格式。
- 子智能体审核和人工阅读审核的交接、反馈、分歧处理和写回证据方式应在协议中可执行。

## 交付物

1. 更新验证策略相关技能说明，写清文档修改选择 `unit_test`、`qualitative`、`rwp` 的边界。
2. 补充字符级断言适用规则，明确“应该断言”和“不应该断言”的场景。
3. 补充自然语言定性审核交接方法，定义子智能体和人工审阅者拿到的审核交接包结构。
4. 补充审核结果写回要求，明确子智能体发现、人工反馈、采纳或拒绝理由、残余风险如何进入 `evidence.md`。
5. 更新反模式文档，把“对自然语言文档默认跑 pytest”与“用脆弱字符断言替代语义审核”列为常见失败模式。
6. 如协议文档测试中已经存在适合的稳定文本契约，可添加或调整最小化测试；不为自然语言语义本身新增脆弱字符串断言。

## 非目标

- 不重写 OpenHarness 的整个验证流程。
- 不引入新的验证方式枚举，继续使用现有 `unit_test`、`qualitative`、`rwp`。
- 不为所有文档建立通用 Markdown 语义评分器或自动审稿系统。
- 不把任务包正文的自然语言质量交给 `pytest` 判断。例如，不用 `assert "清晰" in text` 或完整句子包含断言来证明需求文档写得正确。
- 不修改与本轮协议说明无关的 CLI 行为。

## 约束

- 文档正文使用中文；命令、状态值、YAML 键名、文件名和路径保持英文。
- 本轮改动应保持现有任务包状态机和 `verify_by` 枚举兼容。
- 规则应能被普通 AI 协作者直接执行，避免只写抽象原则。
- 定性审核流程必须保留人工审阅者的最终判断权；子智能体用于扩大盲区和结构化发现。
- 自动测试只能覆盖稳定文本契约或协议结构，不覆盖自然语言语义是否“写得好”。
