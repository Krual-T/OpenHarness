# 仓库地图反模式

本文记录维护 `docs/repo_map/` 时应避免的做法。发现这些问题时，应先收缩地图边界，必要时向用户确认事实。

## 正向规范

`MAP.md` 只保留两个结构：

```md
# <模块名>地图

## 目录作用

- `<下一层目录>/`：说明下一层目录的作用。
- `<直接文件>`：说明当前目录直接文件的作用。
```

除 `# 标题` 和 `## 目录作用` 外，不在 `MAP.md` 中新增其他 section。

`MAP.md` 的每个条目必须采用“职责 + 进入条件”的路由说明：

- `<下一层目录>/`：说明该目录负责什么；说明什么时候应该进入。
- `<直接文件>`：说明该文件负责什么；说明什么时候应该读取。

示例：

```md
- `openharness_cli/`：CLI 工具；修改命令入口、任务包状态流转、初始化、更新、RWP 命令或数据模型时进入。
```

不要只写成：

```md
- `openharness_cli/`：CLI 工具。
```

当某个目录满足以下任一条件时，应新增下一层 `MAP.md`：

- 当前任务需要读取该目录下多个长期子目录或多个长期文件。
- 该目录内存在不同职责边界，继续只写父层会导致条目过长。
- 同一目录在多次任务中反复被访问，且每次都需要重新判断读哪些文件。

## 反模式

- 纳入未被 Git 记录的文档或目录。
  - 除非用户明确要求，否则 `docs/repo_map/` 默认只纳入 Git 记录中的长期资源。
  - 对运行态、本地缓存、临时产物和本地 workflow 产物，只能在稳定入口路由中说明用途，不能把其中具体内容写成仓库事实。

- 越级说明子目录。
  - 每层 `MAP.md` 只说明下一层子文件夹或文档的作用。
  - 例如 `docs/repo_map/tests/MAP.md` 可以说明 `tests/server/` 和 `tests/tmp/`，但不能直接说明 `tests/server/agent_runtime/`。
  - 如果需要说明更深层目录，应在下一层建立对应的 `MAP.md`。
  - 不要因为担心新增地图而把更深层目录继续塞进父层；满足正向规范中的触发条件时，应新增下一层 `MAP.md`。

- 添加多余 section。
  - 不在 `MAP.md` 中写 `## 进入条件`、`## 边界`、`## 排除范围`、`## 维护规则`、`## 常用命令`、`## 使用方式`。
  - 这些规则应放在反模式或规范文档中，不散落到每个地图文件。

- 把地图写成完整文档摘要。
  - 地图只说明目录职责。
  - 地图条目必须说明进入条件，但进入条件应保持短句，不扩写成完整使用说明。
  - 具体设计、实现细节、验证结果和历史结论应留在原始文档、源码或 evidence 中。

- 把本地工作流产物写成仓库事实。
  - OpenHarness skill 的本地任务包目录不纳入仓库地图。
  - 如果本地任务包内容需要长期保留，应先向用户确认，再迁移或摘录到可提交的长期文档。

- 静默修正文档腐坏。
  - 如果地图与实际路径、Git 记录或代码事实不一致，先向用户确认事实，再修改地图或相关文档。
  - 不要把自己的推测直接写成事实。

## 修正方式

- 父层地图过细时，把越级内容移动到下一层 `MAP.md`。
- 地图引用了未被 Git 记录的内容时，删除引用；如果用户明确要求保留，写清这是显式例外和边界。
- 地图内容变成长摘要时，压缩为 `## 目录作用`。
- 地图条目只有目录简介时，补充进入条件；父层条目过长时，新增下一层 `MAP.md` 承载下一层路由。
