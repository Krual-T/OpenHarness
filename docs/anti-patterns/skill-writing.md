# Skill 撰写常见错误

> 本文档记录在 OpenHarness 技能和模板撰写过程中反复出现的错误模式。撰写或修改技能时，应先对照此清单自查。

---

## 1. 完成标准使用情绪化训话式表述

**错误特征**：完成标准（"完成标准"）使用威胁、恐吓或居高临下的口吻，把"自检清单"写成"训话"。

**错误示例**：
- "不能缺失，否则盲区会被静默吞掉。"
- "生产环境从没有这种事。"
- "不接受'基本对应''大体覆盖'这种泛化句。"
- "不能只抄配置，必须能看出实际执行缺口。"

**为什么是问题**：完成标准的读者是正在执行任务的代理或人。训话式表述制造压迫感，且"被吞掉""从没有"这类修辞在实际操作中不可检查。完成标准应该像手术器械清单——冷静、具体、逐项可核对。

**正确做法**：用"应写清什么"替代"不能怎样"。如果需要描述后果，用冷静的中性表述。

**正确示例**：
- "必须填写。未记录的风险会在后续轮次中遗失。"
- "无迁移计划意味着默认'改完即生效'，在生产环境中不可接受。"
- "列出核心需求与关键证据的对应关系。如有未覆盖的缺口，明确写出缺口和接受理由。"
- "明确标出哪些已执行、哪些未执行，不能只罗列命令。"

## 2. 中英术语混用不一致

**错误特征**：模板声明了"命令、状态值、YAML 键名、文件名与路径保持英文"，但正文中仍有大量可翻译的英文术语未翻译，或翻译了但又引用英文原文，造成中英穿插。

**错误示例**：
- "至少写一个 `counterexample`，说明'看起来相关但不属于本轮'的情况。"
- "交代关键 observability 入口（日志、状态、测试观察点、验证产物）"
- "写清楚 key failure modes 是什么"

**为什么是问题**：中英穿插打断阅读节奏。同时存在英文原文和中文翻译时，读者不确定哪个是正式术语。模板自己定的语言规则自己没守住，降低规则的可信度。

**正确做法**：协议锚点（命令、状态值、YAML 键名、文件名、路径）保持英文，其余正文全部使用中文。首次出现的关键术语可以括号标注英文一次，后续只用中文。

**正确示例**：
- "至少写出一个反例——看起来相关但不属于本轮的情况。"
- "说明关键可观测性入口（日志、状态、测试观察点、验证产物）"

## 3. 引言区角色混杂

**错误特征**：模板顶部引用块把"语言规则""写前引导问题""写法建议"三类不同角色的内容混在同一个段落里，读者需要自己分辨每一句是在对谁说话。

**错误示例**：
```
> 章节标题使用中文；正文默认使用中文；命令、状态值...
> 使用前先确认你能回答这些问题：
> - 为什么现在要做这件事...
> 写法建议：先写问题陈述，再写交付物...
```
三条信息挤在一个 `>` 引用块里，三种角色没有分层。

**为什么是问题**：读者需要来回切换阅读模式——读完一条规则（"必须这样做"），立刻跳到引导问题（"你确认了吗"），再跳到写法建议（"建议这样做"）。认知负担高，容易遗漏关键约束。

**正确做法**：按角色分成三个独立标签：

```
> **语言规则**：章节标题使用中文；...
>
> **写前确认**：
> 1. 为什么现在要做这件事？
> 2. 本轮必须交付哪些结果？
>
> **写法要点**：先写问题陈述，再写交付物...
```

## 4. 长句堆叠多条件

**错误特征**：把多个语义层塞进一个段落或一句话，用分号串联多个观点。

**错误示例**：
> 写 System Boundary 时优先用"覆盖什么 / 不覆盖什么"两类句子；写 Trade-offs 时不只写优点还要写代价和放弃了什么；写 Proposed Structure 时优先点名具体模块、接口责任和关键数据/状态模型，不要只写抽象原则。写完后检查：一个不了解上下文的人能不能靠这份文档知道"这一轮设计到底包多大、为什么这样分、关键数据怎么流、失败时怎么办"。

**为什么是问题**：一段话塞了 4 层信息（三个"写 X 时优先 Y"建议 + 一个写后自检问题），读者无法快速提取关键信号。这类文字适合口头讲解，不适合作为模板指令。

**正确做法**：每个要点独立一行。自检问题单独列出。

**正确示例**：
> **写法要点**：写系统边界时同时写清覆盖和不覆盖；写取舍时不只写优点，还要写代价和放弃了什么；写推荐结构时要点名具体模块、接口职责和数据模型。写完后自检：一个不了解上下文的人能否靠这份文档知道这轮设计的范围、结构、数据流向和失败处理方式。

## 5. 教学语言出现在生产模板

**错误特征**：模板中出现"两类句子""三个要点"这种教学语言的句式，把模板读者当成学生在教。

**错误示例**：
- "优先用'覆盖什么 / 不覆盖什么'两类句子"
- "至少写一个 counterexample"

**为什么是问题**：模板不是教材。教材解释"为什么"和"怎么学"，模板只说"写什么"和"写到什么程度"。教学语言会让有经验的读者感到啰嗦，同时拉长了模板。

**正确做法**：直接说要求，不解释为什么这是"两类"或"三个"。模板的目的不是教会读者写作，而是让读者知道这节该填什么。

**正确示例**：
- "写系统边界时同时写清覆盖范围和不覆盖范围"
- "至少写出一个反例——看起来相关但不属于本轮的情况"

## 6. 生造词和内部黑话

**错误特征**：使用项目内部自创的术语或缩写，外部读者或新加入者无法直接理解。

**错误示例**：
- "责任面"（应说"职责边界"或"职责范围"）
- "交代 observability 入口"（"交代"是口语，应说"说明"或"写清"）

**为什么是问题**：生造词只在写作者脑中定义过。读者要么猜，要么查，要么误解。技能和模板是给整个仓库的协作者看的，术语必须能从字面直接理解。

**正确做法**：使用通用的中文技术术语。如果确实需要引入新概念，在首次使用时给出明确定义，且概念名本身要能望文生义。

---

## 7. "为什么"和"写什么"位置颠倒

**错误特征**：在模板章节中，大段解释"为什么要写这个章节"（动机、背景），而具体"应该写什么内容"被埋在尾部或缺失。

**错误示例**：
```
## 非目标
- 用中文写明本轮明确不做什么，避免范围漂移。

完成标准：至少写一个 counterexample，说明"看起来相关但不属于本轮"的情况。
```
第一句解释意图（"避免范围漂移"），第二句写要求。但"为什么"不需要写在模板里——模板使用者的困惑在于"这节到底该填什么"。

**为什么是问题**：模板的核心价值是告诉填写者"往这里填什么"。动机解释可以放在单独的写作指南（如 `references/` 下的方法论文档），放在模板里就是噪音。

**正确做法**：章节标题下直接写"写什么内容"和"完成标准"。"为什么"放到写作方法论文档。

---

## 自检清单

撰写或修改技能文件后，逐一核对：

- [ ] 完成标准用的是"应写清什么"句式，而非"不能/不接受"训话句式
- [ ] 正文中英术语使用一致：命令/状态值/YAML键名/文件名/路径保持英文，其余用中文
- [ ] 引言区按语言规则 / 写前确认 / 写法要点三层分开
- [ ] 没有一段话塞多个条件的长句
- [ ] 没有"两类""三个要点"等教学语言
- [ ] 没有生造词和内部黑话
- [ ] 模板章节只写"填什么"和"完成标准"，不写"为什么"
