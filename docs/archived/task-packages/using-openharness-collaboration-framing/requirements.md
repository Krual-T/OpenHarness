# 需求

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。

## 背景

OpenHarness 的 README 把项目定位为“人机共生协作的工程框架”，强调智能体不是被动执行器，而是可问责的协作方。仓库内 `skills/using-openharness/SKILL.md` 是实际注入给智能体的入口技能，负责在代码修改、设计决策、缺陷修复和新增功能场景中启动任务包流程。

当前入口技能的首段只写了“OpenHarness 是 SDD 驱动的任务包协作协议。具体阶段指令由 CLI 输出的阶段 instructions 接管。”这句话能说明流程来源，但没有把 README 中的协作关系传递给实际执行的智能体。

## 问题陈述

维护者在审查 `skills/using-openharness/SKILL.md` 的入口句时，发现它偏流程说明，弱化了“智能体作为协作方”的项目愿景。使用 OpenHarness 的智能体命中该技能后，可能只理解到“要按任务包流程走”，却没有明确理解自己需要共同收敛问题、挑战假设、记录取舍，并在需求不清、方案不成立或验证不足时提问、反驳或拒绝继续推进。

这次需要现在处理，因为入口技能是协作行为的第一触点。README 的愿景如果没有出现在技能入口，后续阶段指令再细也容易被智能体理解成单纯的流程执行。

## 目标

完成后，`skills/using-openharness/SKILL.md` 同时满足两点：

- `description` 用短句表达这是 OpenHarness 的 SDD 人机共生协作协议，仍保留代码修改、设计决策、缺陷修复和新增功能这些路由触发条件。
- 正文首段明确智能体是可问责的协作方，需要和人共同收敛问题、挑战假设、记录取舍、用证据验证结果，并在条件不足时提问、反驳或拒绝继续推进。

## 交付物

1. 更新 `skills/using-openharness/SKILL.md` 的 YAML `description`。
   验收标准：描述中出现“SDD 人机共生协作协议”，并继续说明该技能用于代码修改、设计决策、bug 修复和新增功能场景。

2. 更新 `skills/using-openharness/SKILL.md` 的正文首段。
   验收标准：首段使用已确认的第一版措辞，明确“可问责的协作方”“共同收敛问题”“挑战假设”“记录取舍”“证据验证结果”，并说明条件不足时应提问、反驳或拒绝继续推进。

## 非目标

本轮不重写 README 的设计哲学，不调整阶段指令、任务包模板、CLI 状态机或任务包创建流程。一个看起来相关但不属于本轮的反例是：为每个阶段都新增“伙伴语气”或“反驳规则”的完整文案体系；这会变成另一轮阶段指令设计任务。

## 约束

改动应保持小范围，只触及入口技能文案和本任务包记录。`description` 必须继续适合技能发现和路由，不能变成长篇价值宣言。正文首段可以承载协作关系和行为边界，但不能重复 README 的完整哲学说明。
