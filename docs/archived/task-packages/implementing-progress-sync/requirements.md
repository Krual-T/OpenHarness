# 需求

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。

## 背景

OpenHarness 的 `plan.md` 已经要求在 `## 实施步骤` 中写可勾选任务，`implementing` 阶段也要求不要等全部完成后才补 `evidence.md`。但现有实现阶段提示没有明确要求执行者在使用环境自带任务进度工具时同步更新 `plan.md`，实际使用中容易出现工具里的进度在变，任务包里的实施步骤却到最后才一次性全勾。

本轮关注 `skills/using-openharness/states/implementing/instructions.md`。参考环境包括 Codex 的 `update_plan`、Claude Code 的任务进度工具，以及其他等价的 todo / task / plan 工具。

## 问题陈述

使用 OpenHarness 的 AI 协作者在实现阶段会同时面对两套进度载体：环境自带的任务进度工具，以及任务包 `plan.md` 中的 `## 实施步骤`。如果提示词没有明确绑定两者，协作者可能只更新工具面板，或者实现结束后才把 `plan.md` 的复选框全部勾上。

这个行为会削弱任务包作为事实源的价值。后续接手者只看 `plan.md` 时，看不到实现过程中的真实推进顺序，也无法判断某个步骤是在完成当时被确认，还是最后补填。

## 目标

做完后，`implementing` 阶段提示词会明确要求：实现者每次使用环境自带任务工具更新进度，改成 `in_progress` 或 `completed` 时，都要同步更新当前任务包 `plan.md` 的 `## 实施步骤`，不能等实现完成后一次性补勾。

这条规则应适用于 Codex、Claude Code 和其他提供等价任务进度工具的环境；没有任务工具时，也应要求逐步维护 `plan.md`。

## 交付物

- `implementing` 阶段提示词中的进度同步规则。
  - 验收标准：提示词要求读取 `plan.md` 的实施步骤，并在使用环境任务工具更新进度为 `in_progress` 或 `completed` 时同步更新 `plan.md`。
- 平台兼容措辞。
  - 验收标准：提示词可以举例说明 Codex、Claude Code 的工具名称，但核心规则不能只绑定某一个平台或某一个旧工具名。
- 阶段结束检查或要点中的一致性要求。
  - 验收标准：实现结束前需要检查环境任务工具、`plan.md` 实施步骤和 `evidence.md` 中间事实是否一致。

## 非目标

- 不实现自动文件监听、hook 或 CLI 机制来强制同步。
- 不改变 `plan.md` 的文件名、章节结构或任务包状态机。
- 不把规则写成只适用于 Claude Code `TodoWrite` 的历史约定；这是一个反例，因为当前目标是跨环境的任务进度同步规则。
- 不新增新的 OpenHarness 专用任务工具。

## 约束

- 需求和实现说明默认使用中文；工具名、状态值、文件名和路径保持英文。
- 规则应位于 `implementing` 阶段，因为同步行为发生在执行实施步骤时；计划阶段最多只负责生成可勾选步骤。
- 不能要求执行者使用当前环境不存在的工具。应写成“如果环境提供任务进度工具则必须使用；如果没有则维护 `plan.md`”。
- 本轮是提示词和协议文档改动，主要验证方式为定性审核，不用脆弱的字符串测试替代语义判断。
