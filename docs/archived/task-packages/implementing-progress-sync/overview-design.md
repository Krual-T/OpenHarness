# 总体设计

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。

## 系统边界

本轮覆盖 `skills/using-openharness/states/implementing/instructions.md` 的行为规则。它负责告诉实现阶段的 AI 协作者如何消费 `plan.md`、如何使用环境自带任务进度工具，以及如何把进度写回任务包事实源。

本轮可以引用但不主要修改 `skills/using-openharness/states/planning/instructions.md` 和 `skills/using-openharness/references/templates/task-package.plan.md`。计划阶段已有可勾选实施步骤结构，当前缺口发生在实现阶段执行时的同步要求。

本轮不覆盖 CLI 状态机、任务包文件模型、自动 hook、文件监听器、IDE 插件或任何新任务工具实现。Codex 的 `update_plan`、Claude Code 的 `TaskCreate` / `TaskUpdate` / `TaskList` / `TaskGet`、旧版 `TodoWrite` 只作为环境任务进度工具示例，不成为 OpenHarness 的硬依赖。

## 推荐结构

推荐方案是在 `implementing` 阶段增加一个独立小节，位置放在开始执行实施步骤之前、`Goal-Driven Execution` 之前。这个小节承担三项责任：

1. 读取当前任务包 `plan.md` 的 `## 实施步骤`，把它作为实现阶段任务清单的事实来源。
2. 如果当前环境提供任务进度工具，则使用该工具跟踪实施步骤；没有任务工具时，直接维护 `plan.md`。
3. 每次更新进度，改成 `in_progress` 或 `completed` 时，同步更新 `plan.md` 中对应实施步骤，禁止最后一次性补勾。

状态模型保持两层：环境任务工具中的瞬时执行进度，以及 `plan.md` 中可持久保存的实施步骤勾选状态。环境任务工具方便当前会话展示，`plan.md` 是任务包事实源。两者发生不一致时，以 `plan.md` 为必须补齐的持久记录，不能用“工具面板里已经更新”替代任务包写回。

## 关键流程

主流程：

1. 实现阶段开始，AI 协作者读取 `plan.md` 的 `## 实施步骤`。
2. AI 协作者判断当前环境是否提供任务进度工具。Codex、Claude Code 或其他工具名只用于识别本环境能力，不改变 OpenHarness 文档结构。
3. 开始某个实施步骤时，更新进度：改成 `in_progress`，并同步 `plan.md` 中对应步骤的当前状态。
4. 完成某个实施步骤时，更新进度：改成 `completed`，并同步 `plan.md` 中对应步骤的复选框或进度记录。
5. 每轮实现循环继续按原有规则追加 `evidence.md` 中间事实。
6. 阶段结束前检查环境任务工具、`plan.md` 实施步骤和 `evidence.md` 中间事实是否对齐。

关键失败信号包括：任务工具里显示完成但 `plan.md` 仍未勾选；`plan.md` 在最后一次性全勾但没有逐步记录；`evidence.md` 写了中间事实但实施步骤状态没有变化；提示词写死某个旧平台工具名，导致另一个环境无法执行。

`uv run openharness rwp list` 返回没有可用运行时工作流包。本轮也不依赖服务、API 或端到端运行时行为，因此不设计 RWP 验证。

## 阶段门禁

进入详细设计前必须满足：

- 规则落点确定为 `implementing` 阶段提示词，而不是 CLI 或 `planning` 模板。
- 平台工具名只能作为例子，核心要求必须写成“环境任务进度工具”和“更新进度：改成 `in_progress` 或 `completed`”。
- `plan.md` 是持久事实源，环境任务工具是当前会话进度视图；提示词必须明确同步方向。
- 降级路径确定：如果环境没有任务进度工具，仍逐步维护 `plan.md`，不能最后补勾。
- 验证路径确定为定性审核，检查语义清晰度、跨环境可执行性和边界完整性。

## 取舍

推荐方案的收益是改动小、直接作用在发生问题的阶段，并保留 OpenHarness 的任务包事实源定位。代价是它仍属于提示词约束，不能像程序逻辑一样强制阻止执行者漏改 `plan.md`。

备选方案一：在 `planning` 阶段或 `task-package.plan.md` 模板里增加更多实施步骤格式要求。这个方案被拒绝，因为现有计划已经能写可勾选步骤，问题不是计划格式不足，而是实现阶段没有把环境工具进度同步回计划。

备选方案二：在 CLI 或 hook 中自动检测任务工具进度并写回 `plan.md`。这个方案本轮拒绝，因为环境任务工具属于不同 agent 运行时，CLI 无法稳定读取所有平台的内部进度状态；强行做会把提示词问题扩大成跨平台集成问题。

备选方案三：只写 Claude Code `TodoWrite` 或 Codex `update_plan` 的专门规则。这个方案被拒绝，因为工具名称随平台和版本变化。专门规则短期看更具体，长期会再次造成环境漂移。

## 推荐图示

不需要新增 PlantUML 图。本轮只有一个提示词落点和两类进度载体，文字列表比图更直接。若后续实现跨平台自动同步，才需要补充平台能力边界图。

## 反思

挑战：是否应该把这条规则写成强制使用 `update_plan` 或 `TodoWrite`，这样更容易让模型照做。

结论：拒绝。Codex 当前工具名是 `update_plan`，Claude Code 新版任务工具已从旧 `TodoWrite` 演进到结构化任务工具；如果 OpenHarness 写死某个工具名，就会把平台差异带进任务包协议。更稳妥的做法是先要求“环境任务进度工具”，再举例说明常见工具名，核心动作统一为“更新进度：改成 `in_progress` 或 `completed`，并同步 `plan.md`”。

验证影响：本轮不能只用字符串存在性检查来证明成功。验证应审核规则是否能让零上下文执行者知道什么时候更新、更新哪个文档、没有工具时怎么降级，以及为什么不能最后补勾。
