# 详细设计

> **语言规则**：章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。

## 可观察性与验证准备

- **主验证路径**：使用定性审核矩阵检查 `implementing` 提示词是否明确要求同步环境任务工具和 `plan.md`，并确认文案使用“更新进度：改成 `in_progress` 或 `completed`”而不是把规则写死成某个单一工具名。
- **辅助验证路径**：执行当前 CLI 可用的任务包校验或全量测试命令，确认文档和任务状态没有破坏仓库基础行为。
- **降级路径**：如果定性审核发现规则含糊、只适用于某个平台、或仍允许最后一次性补勾，回到 implementing 文档修改；如果辅助命令失败，先判断是本轮文档破坏还是既有 CLI 问题，不能用命令失败状态宣称完成。
- **预期证据**：`plan.md` 中的审核矩阵、`evidence.md` 中的审核结论、执行过的命令和结果摘要、版本号更新记录。

## 新增或修改文件

- `skills/using-openharness/states/implementing/instructions.md`：本轮主改动。新增任务进度同步小节，并在阶段结束检查、要点和常见失败模式中补充一致性要求。
- `docs/task-packages/implementing-progress-sync/*`：记录本轮需求、设计、计划、验证和证据。
- `pyproject.toml`、`uv.lock`：按仓库提交约定提升 patch 版本。

不修改 `planning/instructions.md` 和 `task-package.plan.md`，除非实施中发现 `plan.md` 结构无法承载同步规则。当前总设判断是计划结构已经足够。

## 接口

本轮没有 Python API 接口变更，暴露的是提示词契约：

- 输入：当前任务包 `plan.md` 的 `## 实施步骤`。
- 环境能力：当前 agent 环境提供的任务进度工具；可能是 Codex `update_plan`、Claude Code 任务工具、旧版 `TodoWrite` 或等价 todo / task / plan 工具。
- 持久输出：`plan.md` 中实施步骤的勾选状态或进度记录，以及 `evidence.md` 的中间事实。
- 状态词：`in_progress` 和 `completed` 是需要被明确绑定的更新进度动作。

兼容性要求：工具名示例可以出现，但规则不能要求所有环境都存在同一个工具。没有任务工具时，提示词必须给出降级方式：逐步维护 `plan.md`。

可观察性入口：审核者通过阅读 `implementing/instructions.md` 判断规则是否覆盖开始步骤、完成步骤、无工具降级、阶段结束一致性检查和禁止最后补勾。

## 模块内部设计

`implementing/instructions.md` 内部按以下方式落地：

1. 在 `Surgical Changes` 后、`Goal-Driven Execution` 前新增 `## 任务进度同步`。这里是执行前的通用规则，不依赖 unit_test / qualitative 分支。
2. 小节中先要求读取 `plan.md` 的 `## 实施步骤`，再说明任务工具使用规则。
3. 文案使用短句：“每次使用环境任务工具更新进度：改成 `in_progress` 或 `completed`，同一轮同步更新 `plan.md`。”避免写成“把任务状态转换为……”这类绕口表述。
4. 在 `完成后` 或 `阶段结束检查` 增加一致性检查，确认环境任务工具、`plan.md`、`evidence.md` 三者一致。
5. 在 `要点` 增加禁止最后补勾的硬约束。
6. 在 `常见失败模式` 增加“只更新环境任务工具，不更新 `plan.md`”和“最后一次性全勾”的诊断及回退动作。

## 数据语义

本轮关注三个进度载体：

| 载体 | 语义 | 持久性 | 本轮要求 |
|------|------|--------|----------|
| 环境任务工具 | 当前会话的执行进度视图 | 取决于平台 | 可用时使用 |
| `plan.md` 的 `## 实施步骤` | 任务包事实源中的实施进度 | 持久保存 | 必须同步更新 |
| `evidence.md` | 开发中的事实和命令结果 | 持久保存 | 每轮循环追加 |

状态语义：

- `in_progress`：某个实施步骤正在执行。`plan.md` 可以通过进度记录或局部标注体现；不要求发明新复选框语法。
- `completed`：某个实施步骤已经完成。`plan.md` 中对应复选框应从 `- [ ]` 改为 `- [x]`，或在没有复选框时用进度记录说明完成。
- `pending`：未开始状态，不需要每次同步写回，除非初始化任务清单时需要保持一致。

一致性约束：不能出现环境任务工具显示完成而 `plan.md` 没有对应完成记录；不能只靠 `evidence.md` 证明实施步骤完成。

## 阶段门禁

进入实施前必须确定：

- 主改动文件是 `skills/using-openharness/states/implementing/instructions.md`。
- 新规则必须放在所有验证方法分支之前。
- 规则必须覆盖有任务工具和无任务工具两种环境。
- 规则必须使用用户确认的表述：“更新进度：改成 `in_progress` 或 `completed`”。
- 验证使用定性审核矩阵；辅助命令只确认仓库基础行为没有破坏。
- 提交前按仓库约定提升 patch 版本。

## 决策闭合

接受：在 `implementing` 增加独立小节。理由是同步行为发生在实施步骤执行时，放在分支前可以覆盖 unit_test、qualitative 和通用执行循环。

拒绝：把规则写成“必须使用 `update_plan`”或“必须使用 `TodoWrite`”。理由是 OpenHarness 需要跨 Codex、Claude Code 和其他 agent 环境，工具名只能作为示例。

拒绝：修改 `plan.md` 模板来新增复杂状态字段。理由是当前 `- [ ]` / `- [x]` 已足够表达完成状态，`in_progress` 可由进度记录表达；新增格式会扩大协议表面。

延期：用 CLI 或 hook 强制同步。触发条件是后续多次出现提示词规则仍无法改变行为，并且能找到稳定读取各环境任务进度的接口。

## 错误处理

主要静默出错风险是：执行者使用了环境任务工具，用户界面看起来进度正常，但任务包 `plan.md` 没有同步变化。解决方式是在阶段结束检查中加入三者一致性检查，并在常见失败模式中要求回到最近一个步骤补同步，而不是继续推进。

另一个风险是把 `in_progress` 理解为必须改写 `plan.md` 复选框格式。设计上不要求新增 `- [~]` 之类语法；`in_progress` 可以记录在 `## 进度记录` 或对应步骤说明里，`completed` 才对应勾选完成。

如果实施中发现 `plan.md` 没有 `## 实施步骤`，应回到 `planning` 修正计划，而不是在 implementing 阶段临时发明任务清单。

## 迁移说明

实施顺序：

1. 修改 `implementing/instructions.md`，新增任务进度同步小节。
2. 补充阶段结束检查、要点和常见失败模式。
3. 更新 `pyproject.toml` 版本，并同步 `uv.lock`。
4. 在 `plan.md` 写验证设计和审核矩阵。
5. 实施后执行审核和辅助命令，把结果写入 `evidence.md`。

兼容策略：新规则只增加执行要求，不改变任务包文件名、状态机或已有章节。已存在任务包继续可读；后续进入 implementing 的任务开始按新规则执行。

切换点是提示词改动合入后。回滚触发点是新规则导致执行者误以为必须在所有环境使用某个不存在的工具，或误以为 `plan.md` 必须新增复杂状态语法。

## 推荐图示

不需要图示。三个进度载体和两个状态动作可以用表格和短流程表达，图示不会明显降低歧义。

## 反思

验证策略的弱点是定性审核依赖审阅质量。为降低风险，`plan.md` 需要把审核矩阵写到可逐项判定：是否跨环境、是否同步 `plan.md`、是否禁止最后补勾、是否说明无工具降级、是否保持 `evidence.md` 边界。

接口边界成立：本轮只改变提示词契约，不改变 CLI 和文件模型。迁移假设成立，因为新增规则对旧任务包是前向行为约束，不要求重写历史计划。
