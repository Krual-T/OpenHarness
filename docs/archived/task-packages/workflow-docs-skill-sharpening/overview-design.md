# 总体设计

> 章节标题使用中文；正文默认使用中文；命令、状态值、YAML 键名、文件名与路径保持英文。
>
> **使用前先确认你能回答这些问题**：
> - 这轮设计覆盖哪些表面，明确不覆盖哪些表面？
> - 推荐方案的主结构是什么？关键模块边界、接口边界或流程边界是什么？
> - 关键数据/状态模型是什么？哪些全局语义会影响后续实现？
> - 主路径是怎么走的？架构级安全、一致性、权限或兼容性约束是什么？
> - key failure modes 是什么？失败时如何降级、回滚或收缩？
> - 为什么选这个方向，而不是另一个可行方向？至少一个备选为何没被采用？
> - 哪些关系最好通过 PlantUML 图示来稳定表达？
>
> **写法建议**：写 System Boundary 时优先用"覆盖什么 / 不覆盖什么"两类句子；写 Trade-offs 时不只写优点还要写代价和放弃了什么；写 Proposed Structure 时优先点名具体模块、接口责任和关键数据/状态模型，不要只写抽象原则。写完后检查：一个不了解上下文的人能不能靠这份文档知道"这一轮设计到底包多大、为什么这样分、关键数据怎么流、失败时怎么办"。

## 系统边界
本轮覆盖 OpenHarness workflow 文档的三类表面：

- `skills/using-openharness/SKILL.md`：只作为每个会话开始时使用的入口协议，负责说明任务包边界、进入任务包方式、阶段完成时 transition 到对应完成态。
- `skills/using-openharness/states/*/SKILL.md`：作为当前阶段执行说明，负责阶段动作、阻塞条件、回退路径、transition 目标和必要分流规则。
- `skills/using-openharness/references/templates/*`：作为文档模板，负责章节结构、最低写作要求和质量标准。
- `openharness_cli/models/task_package_document.py`、`openharness_cli/validate.py` 和相关测试：只允许同步调整任务包 Markdown 章节 heading 校验，使中文章节标题成为稳定校验目标。

本轮不覆盖 CLI 状态机、hook 触发实现、任务包数据模型、文件名重命名、README 品牌叙述、安装文档或 archived 历史包批量重写。`AGENTS.md` 由智能体框架自动加载，不再通过入口 skill 重复要求读取；受保护文件、输出语言等仓库级约定也不再由入口 skill 维护第二份事实源。

## 推荐结构
推荐采用“三层职责”结构：

1. 仓库级约定层：`AGENTS.md` 由框架加载，承担仓库地图、Python / uv 约定、提交要求和输出要求，所以不需要写在skill中。
2. 会话入口层：`using-openharness` 仅在每个会话开始时使用，建立 SDD 与任务包协作规则；它不承担每次请求的动态路由，也不重复阶段写作指南。
3. 阶段与模板层：阶段 skill 管阶段思考方法、推进步骤、阻塞条件和 transition 目标，模板管文档章节、完成标准和质量标准。阶段 skill 可以引用模板位置，但不复制模板的完整章节写法；模板可以说明如何写对应章节，但不承担阶段方法论或完整状态机教学。

关键约束是单一事实源：仓库级规则只放 `AGENTS.md`；会话入口规则只放 `using-openharness`；阶段思考方式与推进门禁只放对应 `states/*/SKILL.md`；文档结构与质量标准只放对应模板。阶段 skill 不能被削成纯执行清单，它必须继续引导 agent 解决当前阶段最重要的问题。

## 关键流程
会话开始时加载 `AGENTS.md` 和 `using-openharness`。`using-openharness` 只判断任务包边界：不需要任务包时直接回应；需要任务包时通过 `openharness task-package list`、`view` 或 `new` 进入包，然后执行 CLI 输出的当前阶段 skill。

阶段完成时，agent 只需要 transition 到对应完成态，例如 `overview_designing` 完成后 transition 到 `overview_designed`。入口 skill 不展开完整状态机原理，也不解释每个 gate 的内部检查细节。

失败信号主要有四类：入口 skill 重新维护仓库级约定导致与 `AGENTS.md` 漂移；阶段 skill 与模板重复章节写作要求导致职责不清；入口 skill 写入过多状态机细节导致 agent 绕过 CLI 输出的阶段指令；阶段 skill 被压缩成纯清单，导致 agent 知道要写文件却没有被引导完成发散、收敛、挑战前提、比较方案或定义证据契约。

验证相关阶段按“可判断性”而不是“是否能写单元测试”切分。`detailed-design.md` 说明设计如何落地，以及哪些事实能观察它是否成立；`verification-design.md` 按 `verify_by` 设计判断方式和通过标准；`evidence.md` 记录实际观察到的结果和最终结论。这个边界必须同时覆盖 `unit_test`、`qualitative` 和 `rwp`，不能把验证默认收窄为 pytest 或单元测试。

`implementing` 和 `verifying` 都可能接触 `evidence.md`，但职责不同。`implementing` 只能记录开发中的事实：改动文件、中间命令、RED / GREEN / REFACTOR 或等价过程中的观察、发现的设计或验证策略问题。`verifying` 负责最终证据：按 `verification-design.md` 执行验证、比较实际与预期、写最终判定、残余风险和 follow-up。对 `qualitative` 和 `rwp`，实现阶段尤其不能提前给出“通过”结论。

`task_type`、`design_review_mode` 和 `verify_by` 都是工作流分叉点，必须在需求阶段确认并写入 `task-info.yaml`。`brainstorming` skill 负责引导选择、确认并写入这三个字段；后续阶段 skill 只消费这些字段，不重新定义完整选择规则。如果后续发现分类错误，必须回退到需求阶段修正，而不是在中途静默改字段。

文档语言规则集中到模板和任务包文档本身，不由入口 skill 维护。任务包 Markdown 模板和任务包文档的最终方向是章节标题中文、正文中文；命令、状态值、YAML 键、枚举值和路径保持英文。`task-info.yaml` 中 YAML 键、状态值、枚举值和路径保持英文，自然语言字段使用中文。CLI 对必需章节的校验应同步切到中文 heading，不再要求任务包文档保留临时英文兼容锚点。

## 阶段门禁
进入详细设计前，overview 必须满足以下条件：

- 已确认入口 skill 只保留会话入口、任务包边界、进入任务包方式和阶段完成映射。
- 已确认仓库级约定不再放入入口 skill，避免与 `AGENTS.md` 形成第二事实源。
- 已确认阶段 skill 与模板的职责边界：阶段 skill 管阶段思考方法与推进门禁，模板管章节结构与写作质量标准。
- 已确认验证职责边界不绑定单元测试：详细设计定义可落地与可观察性，验证设计按 `verify_by` 定义判定标准，证据文档记录实际观察和结论。
- 已确认 `implementing` 与 `verifying` 的证据分工：前者只写中间事实，后者写最终验证结果、判定和残余风险。
- 已确认 `task_type`、`design_review_mode`、`verify_by` 必须在需求阶段确定；后续阶段只消费字段，发现错误则回退需求阶段。
- 已确认文档语言规则不由入口 skill 维护；模板与任务包文档承载章节语言方向，CLI heading 校验同步改为中文章节。
- 已记录至少一个被拒绝的替代方案，以及失败时如何回退到现有入口 skill 文本。

## 取舍
收益是入口 skill 会明显变薄，后续 agent 更容易知道“先进入任务包，再听 CLI 输出的阶段 skill”，不会在入口层读到仓库约定、完整状态机和阶段写作细节的混合内容。

代价是入口 skill 不再自包含所有规则，读者需要信任框架已经加载 `AGENTS.md`，并在进入具体阶段后继续读取 CLI 注入的阶段 skill。这个代价可以接受，因为本仓库已经把 `AGENTS.md` 作为自动加载事实源，重复写入反而更容易漂移。

被拒绝的替代方案：保留入口 skill 作为完整工作流手册。拒绝理由是它会继续和阶段 skill、模板竞争同一职责，后续每次流程调整都要同步多处文本，正是本任务要解决的问题。

被拒绝的替代方案：把 `task_type`、`design_review_mode` 或 `verify_by` 留到对应后续阶段再决定。拒绝理由是这三个字段都会改变后续路径：任务类型影响是否需要设计阶段，设计确认模式影响人机协作方式，验证类型影响证据设计。如果到后续阶段才第一次选择，前面的需求和设计可能已经基于错误前提完成。

被接受的范围调整：同步修改 CLI heading 校验。接受理由是用户确认不保留英文兼容 heading；如果模板改中文而 CLI 仍只识别英文，任务包 transition 会继续依赖过渡锚点，形成新的职责冲突。本轮仍不改状态流转、hook、命令语义或数据模型。

## 推荐图示
本轮不需要新增 PlantUML 图。三层职责关系可以用短表格或列表表达；图示不会明显降低歧义，反而会增加模板维护负担。

## 总体设计反思
挑战：是否应该在 `using-openharness` 中继续要求先读 `AGENTS.md`，以保证仓库约定不会被漏掉。

结论：拒绝。用户确认 `AGENTS.md` 会由智能体框架自动加载，入口 skill 再写一次会造成职责重复。保留仓库约定在 `AGENTS.md`，入口 skill 只建立会话级任务包协议。

挑战：是否应该在入口 skill 里详细解释状态流转和 gate 检查。

结论：拒绝。入口 skill 只需要告诉 agent 每个阶段完成后 transition 到对应完成态；CLI 和阶段 skill 负责后续推进与具体门禁。

挑战：阶段 skill 是否应该只剩执行清单，避免和模板重复。

结论：拒绝。阶段 skill 的核心价值是引导 agent 用正确方式完成当前阶段：需求阶段要发散和挑战前提，总体设计要探索方案和比较取舍，详细设计要下沉到接口、数据语义和失败路径，验证设计要定义判断契约。模板只承载文档结构和质量标准。

挑战：是否可以把三类分类字段留到后续阶段自然决定。

结论：拒绝。`task_type`、`design_review_mode`、`verify_by` 都是工作流分叉点，必须在需求阶段确认。后续发现错误时，正确动作是回退需求阶段，而不是在中途静默调整。
