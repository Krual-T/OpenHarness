## 系统边界
覆盖范围：
- `task-package.task-info.yaml` 模板中新任务包默认字段。
- `REQUIRED_STATUS_KEYS` 中任务包元数据必填字段集合。
- 任务包创建、验证、状态流转相关测试夹具中对 `done_criteria` 的必填假设。

不纳入范围：
- 不批量迁移历史归档任务包。
- 不为 `depends_on` 或 `scope.areas` 设计新行为。
- 不删除 `verification`、`collaboration` 等当前阶段门禁实际消费的字段。

## 推荐结构
推荐方案：
- 模板层：直接删除 `depends_on: []`、`scope.areas`、`done_criteria`。
- 校验层：从 `REQUIRED_STATUS_KEYS` 删除 `done_criteria`，让缺少该字段不再报错。
- 模型层：删除 `done_criteria` 一等字段；旧 YAML 中存在的这些字段通过 `_extra` 的通用机制保留。
- 测试层：更新临时 `task-info.yaml` 夹具，移除不再必填的 `done_criteria`；增加缺少 `done_criteria` 仍可验证通过的断言。

## 关键流程
主流程：
1. `openharness task-package new` 读取精简后的模板。
2. 新任务包 `task-info.yaml` 不再包含三个低价值字段。
3. `validate_task_package` 只检查仍在 `REQUIRED_STATUS_KEYS` 中的字段。
4. 如果旧任务包仍有这些字段，`TaskInfo.from_dict` 把它们作为 `_extra` 读取并保留。

失败信号：
- 新模板仍出现 `done_criteria`、`depends_on` 或 `scope.areas`。
- 缺少 `done_criteria` 的包仍被报 `missing required key`。
- 旧任务包读取时因额外字段失败。

## 阶段门禁
进入详细设计前必须确认：
- 删除范围限定在新模板和必填校验，不做历史批量迁移。
- `done_criteria` 从必填 schema 和一等模型字段中删除；旧字段仅作为 `_extra` 兼容保留。
- 测试覆盖新模板不含字段和缺字段校验通过。
- 当前任务包在旧校验下临时保留 `done_criteria`，实现移除校验后再删。

## 取舍
收益：新任务包元数据更短，减少没有执行语义的字段误导。

代价：历史任务包仍会包含这些字段，短期内仓库里会同时存在旧形状和新形状。

被拒绝方案：对历史归档任务包做批量字段删除。拒绝原因是会重写历史证据，且不影响新 schema 表面。

被拒绝方案：批量迁移归档任务包。拒绝原因是改动面大，证据历史会被重写，不符合本轮 cost cap。

## 总体设计反思
挑战 1：是否应该彻底删除模型属性？
- 结论：接受。`TaskInfo` 已有 `_extra` 机制保留未知字段，不需要继续把 `done_criteria` 作为一等字段。

挑战 2：是否应该连历史归档一起迁移？
- 结论：拒绝。本轮目标是新 schema 表面，不重写历史证据。

挑战 3：是否应该继续保留 `done_criteria` 作为可选一等字段？
- 结论：拒绝。它不再是当前协议字段，只通过 `_extra` 兼容旧 YAML。
