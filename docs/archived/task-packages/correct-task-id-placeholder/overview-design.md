## 系统边界
覆盖范围：
- `skills/using-openharness/references/templates/task-package.task-info.yaml` 的任务编号占位符。
- `openharness_cli/core/task_packages.py` 中创建任务包和补齐阶段文件时的模板替换表。
- 任务包创建相关单元测试中的模板样例。

不纳入范围：
- 不删除 `done_criteria`、`depends_on`、`scope.areas`。
- 不批量改写历史归档任务包里的叙述性证据。
- 不改变任务编号分配算法和状态机。

## 推荐结构
推荐方案：
- 模板层使用 `<TASK_ID>` 表达任务编号占位符。
- CLI 替换层以 `<TASK_ID>` 为主占位符，同时保留 `<DESIGN_ID>` 的兼容替换，避免外部旧模板立即失效。
- 测试层把临时模板样例改为 `<TASK_ID>`，并断言创建出的 `task-info.yaml.id` 等于分配到的实际任务编号。

责任边界：
- 模板只表达占位符，不负责生成实际编号。
- `create_task_package` 和 `ensure_task_package_stage_files` 负责把占位符映射到实际 `task_id`。
- 测试负责防止模板占位符和替换逻辑再次分叉。

## 关键流程
主流程：
1. `openharness task-package new` 分配实际 `TASK-xxx`。
2. CLI 读取模板文件。
3. 替换表把 `<TASK_ID>` 替换为实际编号，并对 YAML 敏感字段做 JSON quoting。
4. 写出新任务包 `task-info.yaml`。

失败信号：
- 新建任务包的 `id` 为 `TASK_ID` 或 `<TASK_ID>`，说明模板或替换逻辑未闭合。
- 测试中仍出现 `<DESIGN_ID>`，说明旧语义仍在创建路径中传播。

## 阶段门禁
进入详细设计前必须满足：
- 已决定模板占位符统一为 `<TASK_ID>`。
- 已决定 CLI 替换逻辑兼容 `<TASK_ID>` 和 `<DESIGN_ID>`。
- 已决定测试需要覆盖新占位符生成实际编号。
- 已明确字段删除评估只作为答复结论，本轮不执行删除。

## 取舍
选用兼容替换的收益是风险低：仓库内模板改用 `<TASK_ID>`，但外部或测试临时旧模板仍能被创建逻辑处理。代价是代码里短期保留了 `<DESIGN_ID>` 兼容分支。

被拒绝方案：只把模板改成 `<TASK_ID>`，不改 CLI 替换逻辑。拒绝原因是会导致新建任务包残留 `<TASK_ID>`，这是上一轮错误的同类问题。

被拒绝方案：立即删除 `done_criteria`、`depends_on`、`scope.areas`。拒绝原因是这是 schema 精简，不是占位符纠错；其中 `done_criteria` 仍被校验消费，删除需要单独设计迁移。

## 推荐图示
不需要图示。本轮关系是线性的模板替换链路，文字和测试足以稳定表达。

## 总体设计反思
挑战 1：是否只修用户指出的模板一行？
- 结论：拒绝。仓库探索显示 CLI 仍替换 `<DESIGN_ID>`，只改模板会制造新失败。

挑战 2：是否趁机删除无用字段？
- 结论：延期。`done_criteria` 被 `REQUIRED_STATUS_KEYS` 校验和模型序列化消费；`depends_on`、`scope.areas` 当前主要是额外元数据，但删除模板字段会影响协议形状，应另开 schema 精简任务。
