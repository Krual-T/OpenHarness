## 目标
修正任务包 `task-info.yaml` 模板和创建逻辑中的任务编号占位符语义：模板应使用 `<TASK_ID>`，创建任务包时应替换为实际任务编号。

单一成功指标：新建任务包的 `task-info.yaml.id` 是实际 `TASK-xxx` 编号，不会残留 `TASK_ID` 或 `<TASK_ID>`。

## 问题陈述
目标用户是维护 OpenHarness 任务包协议和 CLI 创建流程的协作者。核心场景是运行 `openharness task-package new` 创建新任务包。

上一轮把模板 `id` 改成了无尖括号的 `TASK_ID`，这会让新建任务包直接得到字面量 `TASK_ID`，而不是实际编号；同时 CLI 仍只替换旧的 `<DESIGN_ID>`，即使模板改成 `<TASK_ID>` 也不会生效。当前矛盾是模板语义、替换逻辑和测试样例没有同步。

## 必须交付的结果
1. 修正模板：
   - 验收标准：`skills/using-openharness/references/templates/task-package.task-info.yaml` 第一行为 `id: <TASK_ID>`。
2. 修正创建逻辑：
   - 验收标准：`openharness_cli/core/task_packages.py` 支持把 `<TASK_ID>` 替换为实际任务编号。
3. 同步测试样例：
   - 验收标准：任务包创建相关测试不再使用 `<DESIGN_ID>` 作为任务编号占位符。
4. 评估 `done_criteria`、`depends_on`、`scope.areas` 的实际作用：
   - 验收标准：在最终答复中基于代码消费点说明保留或删除的影响。

## 非目标
- 本轮不删除 `done_criteria`、`depends_on`、`scope.areas`。
- 本轮不批量改写历史归档任务包中的叙述性记录。
- Counterexample：把任务包元数据模型重构成新的 schema，属于后续协议精简任务，不属于本轮纠错。

## 约束
- 协议边界：只修正任务编号占位符和直接相关测试。
- 兼容性约束：可以保留对 `<DESIGN_ID>` 的兼容替换，避免外部旧模板立刻失效。
- 依赖限制：不新增依赖。
- Cost cap：一次小型代码修正、一次相关测试验证、一次聚焦提交。
- 如果要删除字段或修改 `TaskInfo` schema，需要另开任务包设计。
