# 需求

## 背景

OpenHarness 通过任务包把一次开发工作拆成需求、总体设计、详细设计、验证设计、实现和验证等阶段。当前 `standard` 与 `structural` 工作流都会进入 `overview-design.md`、`detailed-design.md` 和 `verification-design.md`，`mechanical` 工作流跳过两阶段设计但仍进入验证设计。

这个模型借用了传统软件工程里的总体设计和详细设计，但在作为通用开发 skill 给其他开发者和智能体使用时，阶段边界不够自然：很多普通任务只是需要一份可执行计划，却被要求写总体设计和详细设计；而真正复杂的模块级任务，又需要保留从整体到局部的设计过程。当前的 `verification-design.md` 只承载验证方案，不能自然表达“先做什么、每一步怎么验、什么时候算完成”。

本任务要重新定义 OpenHarness 的任务复杂度分流和计划阶段，让阶段服务于需求和设计本身，而不是让智能体以推进阶段为目标。

## 问题陈述

OpenHarness 的使用者是把该 skill 用在不同项目里的开发者和智能体。他们在处理单个功能、修复、协议调整或模块级改造时，需要知道当前任务应该写哪些文档、跳过哪些文档，以及每个文档要回答什么问题。

当前存在三个具体问题：

1. `standard` 任务缺少独立的执行计划。实现步骤和验证设计被分散在详细设计、验证设计和实现阶段之间，导致执行时容易靠临场判断推进。
2. `overview-design.md` 与 `detailed-design.md` 的启用条件过宽。普通任务会被要求填写系统边界、关键数据、状态模型等内容，即使任务本身并不需要先做结构拆解。
3. `verification-design.md` 的定位过窄。它只回答怎么验证，没有把实现步骤、分步验收和最终完成判定放在同一张执行清单里，难以承接 OpenSpec `tasks.md` 和 Superpowers plan 中“可勾选子任务”的优点。

结果是：智能体容易把文档当作阶段门禁来填，而不是根据需求判断是否真的需要总体设计、详细设计或计划。文档读起来也容易变成高度抽象的模板话，无法让后来接手的人直接执行。

## 目标

完成后，OpenHarness 应当形成一套更清楚的通用阶段规则：

1. `mechanical` 任务不启用 `plan.md`，也不启用总体设计和详细设计。它只适用于改动很小、判断成本低、通常不跨模块的工作。
2. `standard` 任务启用 `plan.md`，但不默认启用 `overview-design.md` 和 `detailed-design.md`。它适用于需要拆步骤、分步验证、记录执行清单，但不需要先做模块结构设计的常规任务。
3. `structural` 任务启用总体设计、详细设计和 `plan.md`。它适用于模块复杂、影响长期协议、跨模块边界、需要从整体到局部设计的任务。
4. 现有 `verification-design` 阶段被重新定位为计划阶段，`plan.md` 同时包含实现步骤、验证设计和完成判定。
5. 阶段判断条件要写成面向通用项目的协议，而不是只适用于 OpenHarness 本仓库的内部规则。

判断本任务完成的标准是：一个不了解本轮讨论的人，只看更新后的 skill 指令、工作流定义和模板，就能判断某个任务应该走 `mechanical`、`standard` 还是 `structural`，并知道 `plan.md` 与总体设计、详细设计之间的职责边界。

## 交付物

1. 更新工作流定义，使 `standard` 工作流进入计划阶段，不再默认进入总体设计和详细设计；`structural` 工作流保留两阶段设计并进入计划阶段；`mechanical` 工作流不启用计划和两阶段设计。
2. 新增或重命名计划文档模板，使 `plan.md` 明确包含可勾选实施步骤、每步验证方式、最终验证命令或审核方式、完成判定。
3. 更新阶段提示词和任务类型判断说明，让 `mechanical`、`standard`、`structural` 的启用条件围绕改动复杂度、模块结构复杂度、跨模块影响和验证需要来判断。
4. 调整文档校验或任务包模型中对必需文档和必需章节的要求，使它们与新的工作流一致。
5. 补充或调整测试，覆盖三类工作流的阶段流转和文档要求，避免 CLI 仍按旧的 `verification-design.md`、`overview-design.md`、`detailed-design.md` 规则校验。

## 非目标

本轮不重新设计 OpenHarness 的全部任务包协议，也不引入新的任务管理系统。比如，把任务包改造成 OpenSpec 完整兼容格式，或者把所有阶段替换成 OpenSpec 的 `proposal.md`、`design.md`、`tasks.md`，都不属于本任务。

本轮也不删除总体设计和详细设计。它们仍然是 `structural` 任务需要的从整体到局部设计手段；本任务只收紧它们的启用条件，并把普通任务的执行清单移到 `plan.md`。

## 约束

1. 新规则必须适用于通用项目，不能只写成“OpenHarness 本仓库改动不超过几个文件”的内部经验。
2. 阶段命名和文档命名可以调整，但 CLI、skill 指令、模板、校验模型和测试必须保持一致，不能出现流程进入 `plan` 但模型仍要求 `verification-design.md` 的情况。
3. 迁移应尽量保持已有任务包可理解。历史归档不要求批量改写，但当前活跃任务包和新建任务包不能被新规则破坏。
4. 文档语言要直接说明使用者该如何判断，不使用只有模板作者才理解的抽象术语；必须解释“总体设计”“详细设计”“计划”各自负责的问题。
5. 本轮不扩大到实现 OpenSpec 或 Superpowers 的子 Agent 调度能力，只借鉴它们的计划清单和分步验证表达方式。
